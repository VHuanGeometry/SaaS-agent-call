# 多租户 AI Agent 电话营销系统 — 概要设计

> **技术栈**: JDK 21 / Spring Boot 3.2 / Spring Cloud / Nacos / MyBatis-Flex / PostgreSQL  
> **架构风格**: 微服务 + 事件驱动  
> **文档性质**: 概要设计，不涉及代码实现细节

---

## 1. 项目概述

### 1.1 背景与目标

构建一套 SaaS 化的 AI Agent 电话营销平台，使企业客户（租户）能够配置专属的 AI 外呼机器人，自动完成线索筛选、意向识别、话术对答、预约回访等电话营销任务。系统以多租户模式运行，各租户的数据、配置、话术和通话记录严格隔离。

### 1.2 核心能力

- **多租户隔离**: 租户级别的数据、配置、资源全链路隔离
- **AI 对话引擎**: 基于大语言模型（LLM）结合 ASR/TTS 实现自然语音交互
- **可视化话术编排**: 拖拽式话术流程设计，支持意图跳转、条件分支、槽位收集
- **智能外呼调度**: 支持定时外呼、预测式外呼、预览式外呼等多种策略
- **实时通话监控**: 坐席可实时监听、切入/切出 AI 通话
- **数据分析看板**: 通话量、转化率、意向分布、挂断率等多维分析

### 1.3 设计约束

| 维度 | 约束 |
|------|------|
| 语言 & 运行时 | JDK 21，利用虚拟线程、Record 等新特性 |
| 框架 | Spring Boot 3.2 + Spring Cloud 2023.x |
| 数据库 | PostgreSQL 16+ |
| 中间件 | Redis（Redisson）、Nacos、Kafka |
| 通信协议 | SIP（运营商对接）、WebSocket（前端实时推送） |
| 单租户规模 | 支持 500+ 并发 AI 通话 |

### 2.2 服务间通信模式

| 通信场景 | 方式 | 说明 |
|----------|------|------|
| 同步调用（CRUD） | @HttpExchange（Spring 声明式 HTTP 接口）+ Sentinel | 常规查询、配置获取、管理后台操作 |
| 高性能 RPC | Dubbo（Triple 协议） | 流式数据传输、批量任务下发、高频指标采集 |
| 异步消息 | Kafka | 通话状态变更、任务流转、数据埋点 |
| 实时推送 | WebSocket（netty-socketio） | 通话监控面板、坐席切听 |
| 服务发现 | Nacos | Dubbo 服务注册与发现、配置中心 |

### 2.3 Dubbo 与 @HttpExchange 的选型边界

| 通信类型 | 选型 | 典型场景 |
|----------|------|----------|
| 常规 CRUD | @HttpExchange | 租户管理、话术配置、名单查询、报表拉取 |
| 双向流 | Dubbo Triple BIDIRECTIONAL_STREAM | call ↔ ai-engine：音频流推送 + 实时转写流回传 |
| 客户端流 | Dubbo Triple CLIENT_STREAM | campaign → call：一批下发 1000+ 号码 |
| 服务端流 | Dubbo Triple SERVER_STREAM | ai-engine → 监控面板：逐句推送转写结果 |
| 高频指标采集 | Dubbo Triple UNARY / CLIENT_STREAM | analytics：通话状态指标实时上报 |

**选型理由**：
- CRUD 走 @HttpExchange 是因为数据库查询耗时占端到端延迟的 80% 以上，序列化差异被淹没，而 HTTP 生态（Gateway 路由、Knife4j 文档、curl 调试）的开发效率远高于 RPC
- 流式场景走 Dubbo Triple（基于 HTTP/2）是功能性刚需 — HTTP 请求-响应模型无法承载双向流音频传输，Triple 协议基于 HTTP/2 具备全双工流式能力，且原生支持 Java 接口定义，无需 `.proto` IDL

**核心调用链**：
- `campaign → call`：Dubbo Triple CLIENT_STREAM，批量下发号码
- `call ↔ ai-engine`：Dubbo Triple BIDIRECTIONAL_STREAM，音频流推送 + 转写流回传
- `ai-engine → 监控面板`：Dubbo Triple SERVER_STREAM，逐句推送转写结果
- 其余服务间调用（租户查询、话术获取、名单拉取）走 `@HttpExchange`，天然兼容 Gateway 路由和 Knife4j 文档
- 通话过程中 `call-service` 通过 Kafka 事件驱动 `analytics-service` 和 `notification-service` 进行准实时统计与通知

## 4. 多租户架构设计

### 4.1 数据隔离策略

采用 **"数据库级隔离 + 共享基础设施"** 的混合模式：

| 数据类型 | 隔离策略 | 说明 |
|----------|----------|------|
| 租户业务数据（通话记录、线索、话术） | **独立 Schema** | 每个租户一个 PostgreSQL Schema，物理隔离，支持独立备份与迁移 |
| 平台公共数据（系统配置、模型列表） | 共享表 | 所有租户共享，`tenant_id = 'system'` |
| 租户元数据（租户信息、套餐） | 共享表 | 放在 `public` Schema，由 `tenant-service` 管理 |
| 文件存储（录音、报表） | 目录隔离 | MinIO 中按 `/{tenant_id}/` 前缀划分 |

### 4.2 租户上下文传递

```
请求 → Gateway（解析 JWT → 提取 tenant_id → 注入 Header X-Tenant-Id）
     → 各微服务（拦截器读取 X-Tenant-Id → 设置 TenantContext）
     → 数据访问层（MyBatis-Flex 拦截器动态切换 Schema）
```

- **Gateway 层**: 解析 JWT 中的 `tenant_id`，注入 `X-Tenant-Id` 请求头
- **服务层**: 通过 `TenantContextHolder`（ThreadLocal）贯穿整个请求链路
- **异步场景**: Kafka 消息体携带 `tenant_id`，消费者解析后设置上下文
- **定时任务**: 任务执行前显式设置 `TenantContext`

### 4.3 资源隔离与配额

| 隔离维度 | 实现方式 |
|----------|----------|
| 并发通道 | 租户套餐限定最大并发 AI 通话数，`call-service` 分配前校验 |
| 存储容量 | 录音文件按租户累计大小，超配额拒绝新录音 |
| API 频率 | Gateway 层按 `tenant_id` 维度限流（Sentinel） |
| 计算资源 | AI 引擎按租户分配独立线程池 / 虚拟线程组 |

每个意图节点关联：

│  │          │  │          │  │                  │  │

```

### 6.2 模型策略

| 环节 | 推荐方案 | 延迟要求 |
|------|----------|----------|
| ASR | 流式识别（SenseVoice / Whisper），支持 VAD 断句 | < 300ms 首字 |
| NLU | 专用意图分类小模型 + LLM 兜底 | < 200ms |
| 对话生成 | LLM（Qwen / DeepSeek）结合话术模板约束 | < 1500ms |
| TTS | 流式合成（CosyVoice / ChatTTS），支持 SSML | < 500ms 首音 |

**关键优化**: ASR 和 TTS 均采用流式模式，与对话管理管道并行工作，端到端延迟控制在 2s 以内。

### 7.2 JDK 21 特性利用

| 特性 | 应用场景 |
|------|----------|
| **虚拟线程 (Virtual Threads)** | AI 引擎并发处理大量通话会话，每个会话一个虚拟线程，避免线程池瓶颈 |
| **Record** | DTO、VO、事件对象定义，简洁不可变 |

→ call.ended → call.intent_tagged → call.recording.ready
```

- **AI 引擎**: 模型服务独立部署，与业务服务解耦，支持多模型实例负载均衡

## 10. 安全设计

### 10.1 安全分层

| 层次 | 措施 |
|------|------|
| 传输层 | 全链路 TLS 1.3，SIP 信令采用 SIPS |
| 认证层 | JWT（Access Token 30min + Refresh Token 7d），支持租户 API Key |
| 授权层 | RBAC 模型，租户内角色隔离（管理员 / 主管 / 坐席） |
| 数据层 | 租户 Schema 隔离，敏感字段 AES-256 加密存储（手机号、录音） |
| 审计层 | 全量操作审计日志，不可篡改写入 |
| 合规 | 通话录音前播放合规提示音，支持号码黑名单、勿扰时段配置 |

### 10.2 租户安全

- 租户 API Key 使用 HMAC 签名校验，防止伪造
- 跨租户访问检测：数据访问层拦截器校验 `tenant_id` 与当前上下文一致性
- 录音文件访问：预签名 URL，有效期 5 分钟，绑定租户身份

## 13. 风险与待定事项

### 13.1 已识别风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| ASR 方言识别准确率低 | 意图识别错误，对话体验差 | 多模型投票策略，方言场景降级转人工 |
| 运营商 SIP 线路不稳定 | 通话中断，接通率下降 | 多线路冗余，自动切换，实时监控线路质量 |
| LLM 延迟抖动 | 对话响应慢，用户挂断 | 模型预热、本地缓存常见回复、超时兜底话术 |
| 数据隔离漏洞 | 租户数据泄露 | 定期渗透测试，数据访问层自动化校验 |

### 13.2 待定事项

- LLM 模型选型：自建 vs 云厂商 API，需评估成本、延迟与合规性
- 号码资源：运营商线路采购策略（固话 / 400 / 95 号码），需与商务确认
- 合规性：不同地区对电话营销的法规要求差异，需法务评审
